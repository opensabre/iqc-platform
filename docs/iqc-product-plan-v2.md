# IQC 业务模板驱动质检产品方案 V2

状态：目标方案已进入实施，不代表全部功能已实现或可上线。方案基线日期：2026-09-16；当前交付与未完成验收见[实施进度](iqc-v2-implementation-progress.md)。

适用读者：产品负责人、质检运营专家、设计、研发、测试。本文确定产品职责与体验；现状证据、改造清单、兼容与验收见 [实施影响与交付方案](iqc-v2-implementation-impact.md)。界面约束见 [前端 DESIGN.md](../../iqc-platform-admin/DESIGN.md)。

## 1. 产品结论

IQC 应从“用户拼装规则、Agent 和执行模式的技术后台”，转为“专家建设业务模板，质检人员用模板完成检查、评分和画像识别的业务工作台”。

普通用户的主路径固定为：**选择业务模板 → 选择会话并确认少量设置 → 执行并查看结果**。

专家维护路径为：定义检查标准与标签 → 配置检测能力 → 独立设置评分 → 配置推荐执行策略 → 样本验证 → 发布业务模板。

### 1.1 已确认的方向

- 底层规则由高级专家或运营专家维护，普通质检人员不需要学习正则、DLS、提示词或 skills。
- 评分与检测规则分离；同一检测能力可以用于不同业务标准和不同评分方案。
- Agent 只负责 LLM 能力，不持有整个任务的质检模式或规则集。
- 执行策略属于任务执行层；模板提供推荐配置，任务冻结实际采用的策略。
- 业务模板组织规则、评分、标签和推荐策略，让用户按电话销售、客服、催收等场景使用与维护。

### 1.2 本方案建议确认的产品决策

- “质检方案”是可执行的业务配置；“模板”是方案的可复用发布形态，不建立两套独立执行模型。
- 普通用户直接运行已发布模板，不必先复制方案、测试、审批、发布。允许范围内的调整只记录为任务配置。
- 模板内检查与标签可同时执行，不再要求用户在“规则模式”和“标签模式”之间二选一。
- 推荐策略按质检项或识别目标配置，不能用某条普通规则未命中来跳过其他独立检查或画像识别。
- 第一期不做任意流程拖拽编排，不做独立评分引擎产品，不新增一套规则或标签数据库。

## 2. 用户角色与首用门槛

角色是职责集合，复用现有组织权限体系授权；一个人可以兼任，不新增用户体系。

| 角色 | 日常任务 | 默认不需要接触 |
| --- | --- | --- |
| 质检人员/任务管理员 | 选模板、选数据、启动任务、看证据、提交复核 | 规则表达式、Agent、模型、执行图、发布审批 |
| 业务主管 | 看分数分布、问题趋势、画像分布、处理复核 | 底层检测实现 |
| 运营专家 | 维护业务质检项、评分、标签、模板、样本 | 非必要的模型连接配置 |
| 技术/算法专家 | 维护规则、DLS、Agent、模型及工具能力 | 每批业务任务的创建 |
| 平台管理员 | 账号权限、组织范围、模型接入、资源与预算 | 业务检查标准的具体解释 |

新手只需理解三个概念：**模板是检查标准，任务是一次检查，结果是结论与证据**。数据入口再解释“会话”；结果页按需解释“质检项、评分、标签”。规则集、Agent、策略、快照只在专家页和追溯区出现。

## 3. 概念体系与职责边界

| 概念 | 回答的问题 | 包含什么 | 不负责什么 |
| --- | --- | --- | --- |
| 会话 | 检查哪些沟通内容？ | 消息、说话人、时间、业务元数据、完整性 | 检查标准 |
| 检测规则 | 如何识别一个事实？ | 范围、角色、条件、表达式或语义要求、输出定义、版本 | 业务最终扣分 |
| 规则集 | 哪些检测能力经常一起复用？ | 规则引用与明确的组合语义 | 完整业务模板、整个任务评分 |
| 质检项 | 业务要求是否满足？ | 业务说明、适用条件、检测引用、结果解释、证据要求 | 模型连接、分散的隐式扣分 |
| 标签/识别目标 | 会话表达了哪些业务事实？ | 定义、值域、适用主体、证据、未知与冲突处理 | 自动认定违规 |
| 评分方案 | 检查结论如何变成分数？ | 项目分值、评分方式、否决、等级阈值 | 自行检测会话 |
| LLM 智能体（Agent） | 由什么 AI 能力判断语义？ | 角色、提示词、模型、skills、工具、输出契约 | 整体执行模式、规则集、总分 |
| 执行策略 | 哪些检测如何执行与复核？ | 检测顺序、依赖、Agent 引用、超时重试、复核条件 | 业务标准与分值 |
| 质检方案/业务模板 | 这个业务完整检查什么？ | 质检项、评分、标签目标、推荐策略、可调整范围、版本 | 待检查数据与本次运行状态 |
| 质检任务 | 用什么标准检查哪批数据？ | 方案版本、允许覆盖值、数据范围、实际策略快照、进度 | 悄悄改变已发布标准 |
| 质检结果 | 实际发现什么？ | 各项结论、分数、标签、证据、执行状态、复核记录 | 覆盖历史自动结论 |

### 3.1 业务组织结构

```text
业务模板：电话销售质检 V3（已发布方案版本）
├─ 检查标准：开场规范、风险告知、虚假承诺……
│  └─ 检测引用：普通规则 / 正则 / DLS / LLM / 显式组合
├─ 评分方案：基础分、逐项扣分、否决项、等级
├─ 画像识别：贷款意向、职业、房产情况、车辆情况……
├─ 推荐执行策略：逐项检测、可选 AI 复核、异常处理
└─ 使用约束：适用数据、允许调整项、权限、发布版本
    └─ 任务：选定会话 + 模板版本 + 本次参数 → 结果与证据
```

### 3.2 规则分类采用多维属性，不混成一棵树

技术与范围是独立维度，“LLM”不等于会话级，“普通规则”也不代表只能检查一句话。

| 维度 | 建议枚举/展示 | 用途 |
| --- | --- | --- |
| 检查范围 | 单消息、整段会话 | 明确输入边界与完整性要求 |
| 检测方式 | 包含/不包含、正则、结构化条件、DLS、LLM | 专家选择实现方式 |
| 业务目的 | 规范检查、事实/画像识别 | 决定业务结果映射，不决定底层引擎 |
| 适用主体 | 坐席、客户、指定角色、双方 | 避免把客户发言归咎于坐席 |
| 结果语义 | 发现违规、满足要求、提取值 | 避免把所有“命中”都解释为扣分 |
| 适用条件 | 场景、阶段、渠道、是否进入相关业务环节 | 不适用项不得判违规 |

“组合”要区分两类：多个条件构成一个事实的 AND/OR，是检测逻辑；规则命中后调用 AI 复核，是执行策略。不能用一个 ALL/ANY 开关同时表达检测逻辑、项目是否违规和整份评分。

现有 REQUIRED_CONTAINS/REQUIRED_REGEX 是单消息语义，不能仅改中文名称就变成“整段会话未告知”。后者必须定义适用阶段、检查窗口、完整会话以及窗口内是否存在告知证据。

当前适用条件实施（B78–B80，受限草稿能力）：质检项可通过 `appliesWhen: {id, versionNo}` 引用独立的已发布检测规则，明确命中时适用、完整评估且未命中时不适用；条件缺失、错误和争议分别保留未评估、错误及待复核。该引用与检查规则一起冻结和检查停用，不单独计分；不能引用本项自身的检测规则。复杂 AND/OR、时序及阶段识别复用现有结构化规则/DLS，不新建任意脚本引擎。无此字段的历史方案保持原语义。已接入后端草稿结构、依赖与判定，并用隔离 H2 验证创建任务、排队、执行、持久化、失败重试及条件停用；LLM 为受控测试桩，不是实际模型或正式发布端到端验收。专家表单已接入条件选择、固定版本、移除与 LLM 智能体校验；普通标准页按冻结名称解释条件且阻止条件模板任务。组件回归与构建通过，真实浏览器、前后端联调、真实业务样本及旧版本升级保护仍需验收，正式发布暂不允许，不代表上述完整条件体系已交付。

后续验收补充（B81–B82）：隔离 Chromium／Ant 控件已验证条件选择、冻结名称与普通入口门禁，但使用的是合成 API，不能替代真实后端联调。条件草稿任务现冻结为 `iqc-scheme-v2-applicability-v1`，以阻止严格旧协议读取器忽略新字段；无条件任务保留原格式及摘要。实际旧镜像／混合版本验证仍待完成，不能宣称可直接滚动发布或回滚；升级与回滚前置约束见 [部署门禁](deployment.md)。

路线组合补充（B135，受限专家试跑）：逐项路线可与 `appliesWhen` 组合，冻结执行计划使用 `iqc-item-execution-plan-v2`，先判定条件再运行路线；完整未命中保留为不适用，不运行后续阶段。适用条件和路线结果在专家追溯区分别显示。联合标签组合、正式发布和普通模板任务门禁不变；隔离 H2 与前端测试不替代真实模型、样本、浏览器及混合版本验收。

策略变体维护补充（B136，受限专家试跑）：专家方案草稿可在现有表单维护最多 20 个允许策略，逐项配置完整路线、稳定编码、覆盖说明、成本／耗时说明并标记推荐项；增删质检项时同步更新所有变体的路线映射。试跑默认推荐项，多项时显式选择；编码随请求幂等和任务快照冻结。此能力仍不开放正式发布或普通模板任务变体选择；隔离前端测试与构建不替代真实模型、样本、浏览器、旧版本混跑和业务验收。

能力隔离补充（B146，受限专家试跑）：同一批准集合可含“纯规则核查”和“LLM 候选辅助后规则核查”，共享模板 Agent 能力引用；选中纯规则路线时实际任务不带 Agent 快照、不调用模型，选中辅助路线才冻结并使用对应能力。新预览仍校验全部允许依赖，不能因推荐纯规则而隐去失效的 LLM 备选。没有 LLM 备选的纯规则模板不接受多余 Agent 引用；评分仍独立于 Agent 和阶段路线，正式发布门禁不变。

正式任务闭环补充（B154，2026-10-04）：适用条件、显式 LLM 范围、逐项执行路线、允许变体及联合标签组合现已支持完整的本地专家试跑/结果复核/正式发布与普通批量、定时任务。标签识别独立于适用条件门控；与检测规则/输入范围完全相同的上下文可复用，事实、证据、评分和标签共用会话事务。普通用户在模板向导选择批准变体并将选择冻结在请求和任务快照。H2 正常发布版本创建/执行联合路线任务后，评分 FINAL 90、标签为明确 KNOWN false，观察协议与证据落库；正式 33 项迁移后的隔离 MySQL 8.0.34 服务事务／HTTP 场景 49 项通过。真实模型、业务样本、发布审批、真实浏览器、生产数据库/网关及旧版本混合部署仍待验收；详见[实施进度 B154](iqc-v2-implementation-progress.md)。

组合验收补充（B138）：冻结的允许变体路线可与同一质检项的 `appliesWhen` 适用条件组合试跑；条件先判定，命中才运行所选路线，完整未命中仍保持不适用并跳过路线。隔离 H2 四场景覆盖普通路线和变体路线的命中／未命中组合；不开放联合标签、正式发布或普通模板任务。

迁移验收补充（B139）：上述四场景随后在本地隔离 MySQL 8.0.34 上使用正式 Flyway 迁移复验，31 个迁移校验通过、schema 版本为 1.1.30，四项全部通过。该证据不代表生产数据库、旧镜像混合版本、真实模型、业务样本、网关或发布验收完成。

### 3.3 规则集、方案和模板的关系

- 规则集继续供专家复用检测规则，例如“辱骂检测能力包”；普通用户无需先创建规则集。
- 方案承载完整业务契约，例如“外呼销售质检标准”；方案内的质检项以稳定 itemCode 标识。
- 模板是可供别人直接使用的已发布方案，可为系统模板、组织模板；个人常用配置先作为“模板版本 + 允许调整值”的使用预设，不另做完整版本审批体系。
- 修改模板的检查逻辑、分值或发布边界，进入新草稿并发布新版本；旧版本保持可用，除非被明确停用。
- 专家可以“基于此模板创建业务版本”；派生版本记录来源，不自动继承后续变更。

发布历史首期实现（B83）：专家方案页可逐页查看已有不可变发布版本的冻结名称、内容摘要、来源草稿修订及试跑标识，并打开冻结标准的只读展示；每页最多 20 个，按版本号游标读取更早记录。权限复用方案维护并按方案归属校验，停用方案历史仍可读；快照摘要损坏拒绝展示。B83 本身不切换发布指针、不恢复方案、不复制规则、不创建任务，也不把较早版本自动称为“归档”；后续差异、派生来源、普通用户选择历史版本和版本级归档分别由 B85/B86、B151、B152、B153 实现。
历史对比首期实现（B85/B86）：专家可从已加载的两个冻结版本中选基准，按旧→新只读比较方案、质检项及条件规则版本、评分、标签引用、执行路线与运行约束；使用 B83 已校验的冻结快照，不另建历史模型或访问当前目录。当前是列明字段的业务差异视图，不等于完整 JSON／依赖内容差异或实际执行效果比较。派生来源记录（B151）通过新草稿保存；普通用户可选择启用模板的精确历史版本（B152），提交时仍绑定所选版本。

版本级归档（B153）：专家可归档或恢复已被较新版本取代的发布版，复用版本表与发布权限；当前发布版不可归档。归档保留快照、专家历史和既有任务，只从普通模板历史中隐藏该版，并拒绝基于该版创建新任务或派生草稿。恢复后该版重新成为可选择的历史版本，不会切换当前发布指针。方案停用仍是另一项整方案可用性控制。
- 第一期不建立独立全局“质检项库”。质检项作为方案成员，引用已有规则能力，避免再造一套规则管理。

## 4. 三类关键用户流程

### 4.1 新手：三步开始第一次质检

| 步骤 | 用户看到与操作 | 系统负责 | 完成标准 |
| --- | --- | --- | --- |
| 1 选模板 | 选择电话销售/客服/催收等卡片，阅读“检查什么、生成哪些标签” | 只展示可用且有使用权限的发布版本，校验依赖 | 不需要配置规则或创建 Agent |
| 2 选数据与设置 | 选已有会话或上传；选择团队、日期；修改允许的业务参数 | 展示数量、完整性、权限检查、预计消耗与预算上限 | 默认参数即可继续；技术策略默认折叠 |
| 3 确认并执行 | 确认模板版本、会话数、输出和费用提示，点击“开始质检” | 幂等创建并启动任务，冻结配置，展示进度 | 可以进入结果，不需要再次发布或审批 |

可选“先看样例”展示模板专家审核过的样本结果，不强制用户试跑。可选“小批试跑”用于验证数据格式和适用性；它不是普通用户每次运行的审批门槛。

业务参数例子：产品名称、合规告知词表的受控占位值、允许开关的非必检项。必须定义类型、范围、默认值和是否影响结果可比性。不得把自由提示词或任意表达式包装成“简单设置”。

实现边界（B140）：当前普通模板向导只允许任务名、会话选择及受控并发，不开放产品业务参数覆盖。模板任务 API 对所有未声明 JSON 字段返回带字段名的参数错误，不会静默忽略后创建任务。新增业务参数须先由业务方确认字段白名单、类型、取值范围、默认值和比较口径；在此之前按不允许覆盖处理。

### 4.2 熟练质检人员：重复执行与复核

从“最近使用”选择模板或常用设置 → 选择新数据 → 执行。支持复用上次任务设置，但不默认复用上次数据；界面明确模板版本是否有更新。

对疑似错误的检查结论申请复核，指定问题项和证据。复核者可以修正业务结论或标签值并说明原因；系统依据任务冻结的评分规则重新计算复核分数，自动结果不被覆盖。

### 4.3 专家：建设和维护模板

1. 定义业务目标、适用渠道/角色/会话完整性要求，选择系统模板作为起点或新建。
2. 编写质检项的业务描述、适用条件、满足/违规示例，引用已有规则或规则集。
3. 选择标签集合或具体识别目标，明确标签值域、主体和未知/冲突行为。
4. 单独设置评分方式、项目分值、否决、等级阈值。
5. 设置逐项推荐执行策略，必要时引用已发布 Agent；纯规则方案不要求 Agent。
6. 设置普通用户可调整项、预算/并发约束与可见范围。
7. 在同一执行引擎上做草稿样本试运行，查看逐项结论、标签、证据、评分与成本。
8. 完成发布校验，依组织既有审批策略发布；发布不是无条件要求新增审批人或流程。
9. 查看线上反馈与版本差异，修改进入新草稿，不阻止旧发布版本被任务引用。

草稿试运行必须补齐：现有 LLM 规则测试不能直接承担此能力。试跑绑定草稿修订号/内容 hash，变更后旧测试只作历史记录，不能当作新版本验证证据。

## 5. 信息架构与页面规格

### 5.1 普通用户工作台

主导航建议：工作台、业务模板、会话数据、质检任务、质检结果；有权限者增加复核与改进。专家配置作为独立分组，不和日常任务入口平铺。

菜单与按钮/API 权限必须同步复用组织中心；隐藏菜单不等于撤销接口权限。

| 页面 | 主内容 | 主要操作 | 关键状态 |
| --- | --- | --- | --- |
| 工作台 | 开始质检、最近模板、运行任务、待复核事项 | 开始质检、继续查看 | 无模板时提示联系专家；无数据时导入 |
| 模板列表 | 场景、适用对象、检查/标签数量、版本、是否需要 AI | 使用、看样例、收藏 | 无权限/依赖不可用需明确原因 |
| 模板详情 | 检查标准、评分表、标签字典、适用限制、允许设置 | 使用此模板、查看版本 | 技术实现折叠；升级不默认替换用户选择 |
| 创建任务 | 模板、数据、少量业务参数、输出预览 | 试跑、立即执行、定时 | 校验失败定位具体数据或依赖 |
| 任务详情 | 进度、完成/失败/待复核数、消耗、版本、重试信息 | 看结果、重试失败项 | 执行完成不等于所有会话已得到有效结论 |
| 结果列表 | 会话、业务结论、分数/待确认、标签摘要、证据数 | 筛选、查看、导出、复核 | 错误与未评估不可显示为合格 |
| 会话结果详情 | 左侧会话与证据；右侧总览、检查项、画像、复核记录 | 定位证据、逐项复核 | 自动与复核结论明确区分 |

### 5.2 专家配置区

- 方案与模板：业务检查、评分、标签、执行策略、可调整范围、样本测试、版本发布七个区域；先业务后技术。
- 检测规则：按范围、方式、用途筛选，维护正反例和版本；继续复用 DLS 工作台，不创建第二套编辑器。
- 规则集：管理能力包和成员，展示被哪些方案版本引用；组合逻辑与计分逻辑分开展示。
- 标签体系：复用分类、标签组、标签值、规则绑定、标签集合、候选审核；提供“被哪些模板使用”。
- LLM 智能体：能力说明 → 模型/工具/skills → 提示词与输出格式 → 样本验证与发布。
- 模型与工具资产：沿用现有管理入口，保留权限隔离和资产可用性检查。

结果详情默认显示业务质检项，不直接把多个底层规则当成多个扣分点。技术追溯展开后才显示规则、Agent、策略、快照和调用记录。

## 6. Agent 与任务执行策略

### 6.1 Agent 边界

Agent 输入：当前检查/识别目标、适用会话或消息、允许上下文、可选初检事实、目标输出 schema。

Agent 输出：判定或识别值、证据引用、理由、无法判断原因、执行错误。模型可以辅助识别评分档位，但最终分数只能由冻结的评分方案计算。

Agent 不再配置 RULE_ONLY 等任务模式，不绑定主规则集，不决定模板整体分数。模型、MCP、skills 是否允许使用，由能力配置、权限和当前执行节点决定，不通过“纯 LLM/混合模式”硬编码裁剪。

提示词、skills 与工具接口也必须有版本引用；凭据保留安全引用，不能把明文密钥放进任务快照。不得承诺工具外部数据、模型服务在未来仍可完全重现。

### 6.2 执行策略的两层配置

- 模板专家定义：每项的推荐检测路线、复核条件、兼容 Agent、失败策略和资源上限。
- 任务执行层确定：本次选择的允许策略配置、执行参数、实际模型与回退记录，并冻结为执行快照。
- 专家草稿试跑可选择 1–5 次完整路线运行；每轮独立执行所有阶段，按质检项对最终阶段投票，中间阶段结果不能直接计分。平票、任一轮出错/待确认或未达到显式设置的一致率门槛时，该项进入待复核，不按未命中或通过处理。一致率仅描述本次重复运行结果，不代表准确率；试跑请求标识必须同时绑定轮数与门槛，结果追溯保留每轮状态。

普通界面展示“使用模板推荐策略”。若模板允许，可选业务可理解的“快速检查 / AI 复核增强”；必须说明覆盖范围、耗时和成本差异，不能用模糊名称掩盖检查项被省略。

| 执行路线 | 适用目标 | 未命中/异常处理 |
| --- | --- | --- |
| 仅规则 | 明确词语、格式、DLS 时序或组合要求 | 无匹配按项目语义解释；运行失败不是通过 |
| 仅 LLM | 语义判断、上下文理解、事实抽取 | 无法判断进入待复核，不自动认定无问题 |
| 规则初筛 → LLM 复核 | 可被确定性初筛覆盖的违规检测 | 初筛无命中可以结束该项；必须标记为该项策略，不能影响其他项 |
| LLM 候选 → 规则验证 | 先定位候选，再做确定性验证的专项识别 | 未产候选不代表其他检查通过；保留现有模式迁移语义 |

系统当前有四种模式，上表全部保留迁移入口。新模板可以不同项目采用不同路线；不再把整份模板强行压成一种全局模式。

例如：“敏感话术”可先词表后 AI 排除引用；“是否完整告知风险”独立做会话判断；“客户贷款意向”独立做识别。即使敏感话术零命中，后两项仍执行。

### 6.3 依赖与去重

- 展开质检项、规则集、标签绑定，形成带版本的检测依赖清单。
- 同一规则版本、同一输入范围/角色、同一参数与策略上下文的检测可以复用结果；仅 ruleId 相同不足以去重。
- 同一检测事实同时供质检项和标签消费，不意味着重复调用或重复扣分。
- 项目组合需明确“必须全部满足/任一满足/显式条件”，禁止依赖全局 ALL/ANY 隐式影响整张评分表。
- 第一阶段只支持固定路线与有限依赖校验，禁止环路；不引入任意可执行脚本与自由 DAG 设计器。

## 7. 检查结果与评分体系

### 7.1 三层结果语义

底层检测事实建议标准化为 MATCH、NO_MATCH、UNKNOWN、ERROR、SKIPPED；原始内容与 evidenceRefs 保留。质检项再根据“命中是违规还是满足要求”映射为业务结论。

| 业务结论 | 含义 | 评分处理 |
| --- | --- | --- |
| PASS | 适用且满足要求 | 正常计算 |
| FAIL | 适用且不满足要求 | 按该项评分政策扣分/不得分 |
| NOT_APPLICABLE | 当前业务不适用 | 不扣分；得分制剔除分母 |
| REVIEW_REQUIRED | 证据不足或检测冲突 | 该项待确认，阻止产生最终分数 |
| ERROR | 检测执行失败 | 展示错误，不能算通过 |
| NOT_EVALUATED | 应检查但尚未检查 | 显示缺口，不能算通过 |

业务不适用是显式适用性判断；策略跳过或无证据不能直接伪装成不适用。

单项展示：标准说明、适用条件、实际结论、证据、理由、评分影响、是否人工修正。多消息命中可有多份证据，但一个业务质检项在同一会话默认只计分一次。

### 7.2 独立评分方案

第一阶段每个方案版本选择一种评分方式，不混用，不引入自定义公式语言：

1. 扣分制：基础分默认 100，最终分数 = max(0, 基础分 − 各 FAIL 项扣分之和)。每项扣分由方案设置，规则本身不拥有最终扣分权。
2. 得分制：最终分数 = 100 × 适用项实际得分之和 / 适用项满分之和。第一阶段支持满足得满分、不满足得零分；后续再支持专家定义的离散评分档位。

两种方式均支持明确的一票否决项：该项 FAIL 时业务结论为“不合格（否决）”，完成评分后最终分记 0，保留其他项结果与普通计分明细。

补充规则：

- 有未解决的计分项时 finalScore 为空，展示“待确认”及已知分数影响，不将临时数用于正式排名。已确定的否决可立即展示，但剩余覆盖缺口仍须显示。
- 非计分标签识别失败不阻止已完成的质检评分，任务显示“部分输出失败”。检查完整率与标签识别完整率分开展示。
- 全部计分项不适用时显示“无适用评分项”，不是满分；仅打标任务显示“仅识别标签”，无评分。
- 总分等级阈值由方案设定，阈值区间必须无重叠、无歧义；规则风险等级与总分等级分别展示。
- 两个质检项如果实际重复描述同一业务责任，发布前给出重复扣分风险提示；技术去重不能替专家决定业务责任是否重复。
- 调整分值属于标准变更，默认不允许普通任务用户修改；若业务确需允许，必须声明范围并标记为不同评分配置，统计不得混为一个标准。

### 7.3 不沿用旧 ALL/ANY 评分作为新默认

现有规则集整体 ALL/ANY 会影响命中与扣分，新方案默认逐质检项评分。旧任务按原计算政策展示；迁移模板时必须显式选择保留旧政策或采用新政策，不能偷偷重算历史结果。

## 8. 标签与业务画像

标签是事实输出，不是“另一种违规”。继续复用现有标签分类、标签组、标签值定义、标签集合与候选审核能力；同一模板可同时产生分数与画像。

### 8.1 标签定义

每个识别目标需要：业务名称、主体（当前客户/坐席等）、值域、证据要求、是否单值、冲突规则、缺失规则、敏感性与可见范围。现有类型不能满足枚举、多值或文本时，先评估最小扩展，不建立平行标签模型。

| 例子 | 建议定义 | 禁止默认推断 |
| --- | --- | --- |
| 贷款意向 | 明确有意向/明确无意向/待确认；未提及为未知 | 提到贷款即有意向 |
| 房产情况 | 有/明确无/未知/冲突 | 沉默等于无房 |
| 车辆情况 | 有/明确无/未知/冲突 | 有房推断有车 |
| 职业 | 受控职业枚举；允许证据不足 | “工程师”自动等于“白领”或收入水平 |
| 有房有车 | 基于两个已知原子事实的显式派生标签 | 缺一个事实仍判满足 |

派生映射应由专家明确定义并版本化，第一阶段可先不支持任意派生，只保留原子标签。第三方转述、假设、历史情况、引用他人话语不能默认归到当前客户。

### 8.2 识别结果状态

- KNOWN：有明确值与证据，包括明确否认，例如 hasHouse=false。
- UNKNOWN：未提及或证据不足；reason 区分未提及/主体不明/信息不足。
- CONFLICT：同一主体存在冲突陈述，保留候选与证据；不得固定取首个命中。
- ERROR：识别或结构解析失败。

confidence 如来自模型自报，仅标为“模型自评”，不宣传为正确概率；多次运行一致率也不能冒充准确率。标签没有证据时不能靠默认值伪造确定事实。

自动候选标签只能进入现有候选审核流程，不能自动扩充生产标签字典或改变模板范围。普通任务默认关闭自动扩展；专家在允许场景下开启。

### 8.3 标签结果与人工处理

每个值可回溯标签版本、来源规则/Agent、会话消息、主体、识别时间与修正记录。用户按权限查看、筛选、导出；导出包含未知/冲突状态，不能只导出命中的正向标签而丢掉覆盖情况。

修正标签不默认改分；只有模板显式把该事实作为某质检项输入时，才触发依赖项重算，并保留自动与人工修正链路。

## 9. 任务、数据与版本生命周期

### 9.1 数据与任务

第一阶段复用文件/ZIP 导入、API 会话接入及已有查询，输入以已结束的文本会话为主，不把实时语音、ASR、流式告警作为本次前置工程。

导入时校验说话人、时间、空消息、重复记录、所属团队与完整性。缺失必要角色或会话不完整时，明确哪些项目不可判定；“没有发现告知”不能在截断文本上直接认定未告知。

任务类型复用批量、定时、抽样。批量冻结选定会话清单；定时任务创建时冻结配置，到执行时按授权范围解析数据筛选条件并记录清单；抽样保存筛选条件、种子、候选范围和最终样本。

V02 本地实现状态（B141，2026-10-02）：已发布模板可创建定时任务。创建时固定模板版本、依赖、并发、数据权限范围和筛选条件；目前普通向导筛选已导入会话，可选文件名并限制最大会话数，数据清单在到期时由现有 dispatcher 解析。没有新增调度表或执行器。H2 与隔离 MySQL 8.0.34 验证了排程后修改草稿不改变执行、到期前新增匹配会话可被选中、重复请求幂等和上限遵从发布版本。生产调度、真实浏览器/网关及跨版本部署还未验证。

失败重试沿用原任务的配置和数据清单，只重试失败执行单元；“按新模板重跑”创建关联的新任务。两者在列表与统计中必须可区分。

创建并开始需幂等；取消保留已产生结果和未执行数量。暂停/恢复仅在执行引擎具备可验证语义时提供，不把“停止刷新页面”当作暂停。

### 9.2 生命周期

方案：草稿 → 已验证 → 待审批（按组织策略可选）→ 已发布 → 停用/归档。草稿修改会使“已验证”失效；编辑新草稿不改变旧发布版本状态。

任务：待执行/等待定时 → 执行中 → 完成/部分失败/失败/取消。待复核作为结果业务状态，不与执行中的技术状态混淆。

结果：自动结论 → 申请复核 → 复核结论；保留多次复核记录与操作者，不能覆盖原始事实。

### 9.3 三次冻结

1. 发布方案：固定规则、规则集展开成员、标签与值定义、Agent、评分和推荐策略的具体版本，不只存最新记录 ID。
2. 创建任务：固定所用方案版本、允许调整值、实际执行策略、依赖快照；未到执行时才解析的定时数据范围单独记录。
3. 执行记录：保存实际模型/工具版本或标识、回退选择、调用参数、错误、重试与证据定位信息；会话内容需保留可定位的修订号或内容 hash，并遵循数据保留策略。

已发布模板更新只提示差异；正在执行和历史任务不自动升级。依赖被安全停用时，新任务阻止启动并明确原因；在途任务按平台停用策略处理，不静默替换成其他模型/规则。

## 10. 结果、分析与质量改进

### 10.1 结果展示顺序

先展示业务结论与有效分数、关键问题、画像摘要和覆盖完整性，再展示逐项证据；技术日志放在追溯区。得分、业务合格性、执行成功率是三个不同维度。

缺失类检查没有一句“违规原话”时，展示检查范围、适用事件、已检索窗口与缺失说明，不能伪造证据片段。

### 10.2 统计口径

- 质检概况：选中/已执行/有效完成/错误/待复核会话数，保留分母。
- 质量分析：各项违规率、评分分布、否决率；不适用、未评估和错误独立统计。
- 标签分析：已知值分布、未知率、冲突率、识别失败率；“有意向占比”注明是全部会话还是已知意向会话作分母。
- AI 与执行：耗时、调用与消耗、模型错误率、复核改判率；人工复核样本上的改判率不直接称为全量准确率。
- 对比按方案版本和评分配置分组；不同分值/覆盖范围不得直接混排，跨版本展示差异提示（评分制、基础分/合格线、逐项分值/否决与项目覆盖）。
- 同一会话重跑沿用现有 `TaskExecution.id`／结果 `executionId` 作为执行实例；业务报表必须明确选择任务当前结果、首次、最新或指定执行实例。首次/最新在同一冻结方案内每会话只计一次，任务内按执行尝试号排序而非依赖结果写入时间；指定实例精确读取且不回退，避免把重跑累计成新增客户或跨运行混分。

复用现有反馈、复核、样本沉淀能力，把反馈对象从旧结果扩展到质检项与标签；是否建设员工申诉门户另立需求，不作为本次闭环前置条件。

## 11. 示例：电话销售业务模板

以下为产品演示配置，不是法律或行业合规标准；具体标准由业务负责人审核。

| 项目 | 实现示例 | 业务判定 | 评分 |
| --- | --- | --- | --- |
| 开场身份说明 | 指定阶段规则/DLS | 适用窗口中缺失身份说明为 FAIL | 扣 5 |
| 产品风险说明 | 会话级 LLM | 进入产品介绍后未完整说明为 FAIL | 扣 20 |
| 不当承诺 | 规则候选后 LLM 复核 | 确认坐席作出被禁止承诺为 FAIL | 扣 30 |
| 辱骂客户 | 规则候选后 LLM 复核 | 确认直接辱骂而非引用为 FAIL | 一票否决 |
| 下一步安排 | 会话级检查 | 进入跟进阶段但未明确安排为 FAIL | 扣 10 |

附加识别：贷款意向、房产情况、车辆情况、职业；均不扣分。推荐路线由模板设置，普通用户只选择产品名称、团队和数据范围。

例：风险说明、下一步安排失败，其余通过，分数为 70；客户明确说无房但没有提车，则房产=false、车辆=UNKNOWN。没有敏感话术命中，也必须完成风险说明与客户画像识别。

若风险说明判断失败，则最终分数显示待确认，不能因系统错误显示 100 或 0；若只有车辆识别失败，质检分数仍为 70，并提示画像部分失败。

## 12. 范围、交付与待确认事项

首期必须闭环：已发布模板直接使用、混合检查与标签、独立评分、Agent 解耦、版本冻结、草稿试跑、结果与基本复核适配。不能仅上线新的导航名称而继续要求新手创建 Agent。

后续增强：离散评分档位、复杂派生标签、批量版本升级对比、更丰富模板运营、成本优化和质量评测。自由流程编排、实时语音、独立员工申诉门户不在本次范围。

建议上线验收的易用性目标（待实测，不是现状成绩）：

- 在模板已发布、数据可用的前提下，新手不接受规则/Agent 培训，三步完成任务提交。
- 5 名目标用户中至少 4 名在 10 分钟内独立完成“选模板、选数据、执行、定位一条证据”；模型运行等待单独记录。
- 纯规则模板创建任务不出现 Agent 必填；默认路径不出现正则/DLS/ALL/ANY 等技术字段。
- 每条扣分能回到质检项、冻结评分政策与证据；每个标签能解释已知、未知、否认或冲突。

评审时需确认：业务模板的发布责任人和审批策略；首批模板及其业务标准；允许用户调整的具体字段；得分制是否与扣分制同批上线；模型预算与数据保留策略。未确认项采用本文保守默认，不应由研发自行扩大范围。
