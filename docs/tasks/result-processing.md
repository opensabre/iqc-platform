# 多引擎结果处理

此模块实现原型第三步“结果处理”的后端计算能力。它消费完整 `EngineExecutionResultSet`，不修改或覆盖其中任何引擎输出。

## 复用与职责

- 评分复用 `InspectionScoring` 的政策、范围校验和计分实现，不另造评分器。
- 标签类型复用 `LabelFactEvaluator.validValue`；发布版本和可见范围复用 `LabelResolutionService.resolve`。
- 新增的 `TaskResultProcessingConfiguration` 只描述本次任务怎样把各引擎观察值映射为质检结论或标签值。旧方案/规则结果投影没有这一独立多引擎输入契约，因此在既有 `TaskResultProcessor` 接口下增加 `ConfiguredTaskResultProcessor`，不新增持久化表或入口。

## 显式配置

版本为 `iqc-task-result-processing-v1`。启用质检时必须提供已有 `iqc-score-v2` 评分政策、逐质检项的引擎映射和汇总规则；基础分、及格线和项目分值由请求指定，原型示例不是默认业务标准。

每个质检引擎都要明确 `onHit` / `onMiss` 为 PASS 或 FAIL，不能把命中天然解释为违规。每个标签引擎明确命中/未命中的值；JSON null 表示未知，不代表新标签值。映射必须符合目标标签已有值编码和类型。

首个可选择的汇总规则为 `REQUIRE_AGREEMENT`（全部已配置引擎结果一致才确定），必须在配置中显式声明；不默认根据顺序选优或忽略失败。不同观察值可以通过明确映射形成相同业务结论，原始观察仍保留。

`TaskResultProcessingService.freeze` 检查计划中的每个引擎恰好映射一次，操作与目标完全匹配，再解析并冻结实际已发布标签定义。客户端不能把任意 targetId 或自报类型当作合法的标签写入目标。

## 结果与证据

处理输出 `iqc-task-processed-results-v1` 包含：

- 每个质检项的全部来源、原观察值、映射结论、证据 ID 和汇总状态。
- 复用评分器得到的分数、计分明细及完整性；同一质检项只计一次分。
- 每个标签的值编码/类型、所有候选及确定/未知/冲突/错误状态。
- 来源结果集、全部引擎结果 ID 和输入快照 ID；原始模型响应及失败记录留在源结果集中。

一致且齐全时为 KNOWN；不同映射值为 CONFLICT；失败或无效输出保留 ERROR；缺失、跳过、未知映射保留 UNKNOWN。存在未解决质检项时分数为 PENDING / null，不能充当通过或零分。质检处理失败不抹掉独立打标结果，确定的布尔 false 标签也会保留。

处理器不推断自然语言引文，不自动新增标签，也不把执行顺序当作结果优先级。没有收到的响应不会被伪造为证据。
