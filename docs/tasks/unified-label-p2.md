# 统一标签 P2：执行快照基础

本批复用 `iqc_inspection_task`、`iqc_task_execution`、原队列和会话执行器。现有任务保存配置预览但没有独立引用定义，执行记录也没有配置或选数快照，因此对原表做最小扩展，不新增任务模型或调度平台。

## 已实现

- 任务保存 `unified_configuration_json`：仅引擎顺序、标签选择方式/ID 和 Agent 引用，不接受客户端规则正文。
- 创建时校验生成预览；首次排队在原 REPEATABLE_READ 事务内，按执行用户权限重新冻结精确版本的标签、规则、动作及 Agent。ALL 在此时重新解析。任一步失败回滚队列认领与快照写入。
- `iqc_task_execution.configuration_snapshot_json` 保存当次完整配置，`selection_snapshot_json` 保存选择定义、运行时随机种子、会话 ID 和消息数。重试和暂停恢复继承上一执行快照，不重新选数或解析新版本。
- 统一执行必须具备配置快照和 run_id，缺失时明确拒绝执行，不回退任务预览配置。
- 新统一任务动态选数为空时，仍创建零条目的执行记录并正常完成，不调用引擎。

## P2 分页增量

统一任务使用 `ConversationQueryService.visitForExecution`：条件选数以 ID 游标每页 500 条回调消费；随机模式复用已有全范围有界堆抽样，再以最多 500 条交付。任务继续保存会话 ID 名单及总数供详情和重试使用，不保留全体会话对象。

消息条目按会话、每页 500 条创建，使用 `(sequence_no,id)` 复合游标，重复序号不导致漏消息。执行阶段每个窗口最多加载并发数个会话的条目/上下文，Future 数量同样有界；结果计数在数据库聚合。查询复用既有 `(task_id,conversation_id)` 索引并限制 execution_id。旧任务执行分支保留。

内存仍包含完整会话 ID 名单、单会话内容，以及旧重试/恢复路径的条目清单；这些不是无限规模保证。后续需在真实负载下验证超长会话、海量 ID 和恢复路径，不能仅凭分页接口宣称百万会话能力。调度和周期轮次隔离见下文。

分页增量验证：96 项通过（选数 5、执行器 36、事务物化 54、统一生命周期 1）。新增场景证明消费第一页后才查询下一页、消息重复序号跨页不丢失、12 个会话在并发数 3 下最大活动窗口为 3，且每个条目查询同时约束 task_id/conversation_id/execution_id。旧路径回归通过；未用这些测试推断生产性能上限。

## P2 触发与轮次增量

统一创建接口要求 trigger，不提供旧模式或手动触发兼容分支。创建页固定为数据筛选、规则与标签、触发计划、任务确认四步。立即执行在事务提交后启动；定时和周期任务复用现有轮询器与执行队列。定时输入及 Cron 使用 Asia/Shanghai。启停通过 PUT /tasks/{id}/enabled；停用不打断正在运行的执行，取消任务同时停用后续触发。

调度以任务行锁串行认领，运行、排队、暂停中的任务不产生重叠执行；错过多个周期只补一个轮次，下一时间从本次认领时刻计算。每个新轮次 run_id 为首次执行 ID，重试和恢复继承同轮次及快照；检查点查询严格限制 run_id，不跨周期复用输入或结果。冻结失败回滚认领及执行记录，调度器记录任务失败并计算下次周期，历史执行不改写。

后台冻结采用服务端保存的创建或重新启用时的数据授权范围，调用结束恢复线程上下文。当前不逐轮重新校验用户角色、组织或权限撤销，生产启用周期任务前须明确权限变更后的生效要求。未修改基础服务和框架。

V1.1.40 扩展既有任务触发配置、启用标志与执行 run_id 及索引；先执行迁移再部署应用。不为缺少必要快照的旧统一执行设计回退策略。
