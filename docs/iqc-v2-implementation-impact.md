# IQC V2 实施影响、兼容与开发交接

状态：已获用户“按这个实施”授权，正在实施；本文保留 2026-09-16 的改造基线，不是完成或上线声明。当前实现与验证范围见[实施进度](iqc-v2-implementation-progress.md)。

主方案：[业务模板驱动质检产品方案](iqc-product-plan-v2.md)。本文基于本地源码静态核验，不代表线上环境、性能或历史数据分布已验证。

## 1. 核验基线与结论

- 后端 `iqc-platform` 基线：`282b9e0`；前端 `iqc-platform-admin` 基线：`0ed22a5`。
- 已有规则、规则集与版本、DLS、四种执行模式、Agent 资产快照、会话导入、任务、分层结果、标签体系、反馈/复核/样本能力。
- 缺口不是“从零做质检”，而是业务配置聚合缺位、技术职责耦合、版本引用不足、评分和标签语义需要明确。
- 本次建议新增的核心领域是“版本化业务方案”；检测、标签、组织权限、执行与复核尽量扩展现有能力。
- 不需要修改 `opensabre-framework` 源码。如实现中发现确需修改，应另行说明影响并获取批准。

## 3. 目标领域模型与复用边界

### 3.1 建议新增的逻辑实体

以下是逻辑契约，不是已经存在的表名或最终 DDL。研发应先核对现有版本/发布通用能力再确定物理设计。

| 逻辑对象 | 核心内容 | 边界 |
| --- | --- | --- |
| InspectionScheme | 稳定标识、名称、业务场景、所有者/范围、类型、当前发布版本指针、停用状态 | 模板与自定义方案共享聚合；不新增第二套模板执行主表 |
| SchemeVersion | 不可变版本、项目定义、评分政策、标签目标、策略配置、允许覆盖 schema、依赖清单、内容 hash | 已发布不可修改；草稿与发布状态分离 |
| SchemeItem（可作为版本内容） | itemCode、描述、适用条件、检测引用、结论映射、证据要求 | 初期无需全局质检项主数据中心 |
| ExecutionSnapshot（扩展任务） | scheme/version、覆盖值、执行路线、依赖版本/内容、预算、schemaVersion、policyVersion | 替代从 Agent.mode 推断新任务策略 |
| ItemEvaluation（扩展分层结果） | 项目结论、证据、来源检测、适用性、评分影响、执行状态、复核状态 | 底层规则结果仍保留为事实来源 |
| ScoreBreakdown（可作为结果结构） | 基础分/满分、项目贡献、否决、最终/待确认状态、政策版本 | 不建立独立检测引擎 |

方案版本可先采用“主记录 + 版本记录 + 结构化配置/依赖清单”的最小模型。是否把项目、策略拆表应由查询和约束需求决定，不为每个产品名词单独建表。

发布历史实施补充（B83）：复用 `iqc_inspection_scheme_version`，不增加持久化模型或迁移。新增专家只读 GET `/api/iqc/schemes/{id}/versions`，复用 `iqc:scheme:manage`；方案归属先于查询校验，20 条版本游标页与摘要校验限制读取范围。前端方案维护页复用已发布标准只读向导，不加载当前规则、Agent 或会话。停用历史可读不等于恢复运行；普通目录、版本指针、任务策略与评分都不变。网关新端点注册仍须环境验收，版本级归档、切换及派生复制不在本批实现范围。

### 3.2 必须扩展而非重建的能力

- 规则/规则集的编辑、版本、发布、DLS 运行时与证据。
- 标签分类、标签组、值定义、绑定、集合、候选审核与结果投影。
- Agent 的模型/MCP/Skill 资产管理与快照、现有 LLM provider。
- 任务队列、批量/定时/抽样、执行进度、数据导入和去重。
- 分层结果、反馈、复核与样本；组织中心的角色、菜单/API 资源和数据范围。

现有规则集无法承担完整方案，因为它缺少独立计分、标签目标、受控参数、执行策略及依赖版本锁定；现有静态模板物化也无法承担完整可执行模板。这是新增方案聚合的具体理由，而非仅为重命名新建持久化体系。

## 4. 接口与执行契约草案

下面是研发讨论用契约示例，路径与字段均为建议，不能当作现有 API 使用。

### 4.1 方案与试跑

- 查询模板：仅返回当前用户可使用的发布版本及能力可用性；读取与使用权限分别校验。
- 保存草稿：携带 expectedRevision，防止多人覆盖；返回 revision/hash。
- 试跑草稿：输入 draftRevision、样本 ID/授权临时样本、允许参数，返回 trialId；限制样本数和预算，建议默认最多 20 段、可由平台配置。
- 发布方案：输入验证记录与预期修订号；校验所有依赖版本、评分、标签类型、输出契约、允许参数、权限、路线与预算。正式发布不能隐式发布依赖草稿。
- 版本比较：显示检查项、评分、标签、策略和依赖变化，不仅比较 JSON 文本。

### 4.2 新任务请求

```json
{
  "schemaVersion": "iqc-task-v2",
  "schemeId": "sales-standard",
  "schemeVersion": 3,
  "dataSelection": { "type": "EXPLICIT", "conversationIds": ["c1"] },
  "overrides": { "productName": "产品A" },
  "executionProfile": "RECOMMENDED",
  "runAt": null,
  "startImmediately": true,
  "idempotencyKey": "client-generated-key"
}
```

新请求不必提供 agentId/ruleIds。后端从固定方案版本解析必要能力，验证覆盖白名单和数据权限，再冻结快照。客户端不能提交任意 execution graph 绕过方案限制。

旧任务请求继续走 v1 兼容处理；不得根据“字段恰好为空”猜测策略版本。idempotencyKey 应与主体/操作和请求内容绑定；同 key 不同内容返回冲突。

### 4.3 业务结果契约

最少应包括：taskId/runId、conversationId、schemeId/version、configurationHash、executionStatus、qualityConclusion、scoreStatus、finalScore、itemResults、labelResults、coverage、reviewState。

- itemResults：itemCode、status、reason、evidenceRefs、detectorRefs、scoreContribution、policyVersion。
- labelResults：labelId/version、subject、state、value、candidates、reason、evidenceRefs、sourceRefs；UNKNOWN 不与 false 混用。
- coverage：预期/完成/不适用/待复核/错误/未执行检查数量；标签识别单独计数。
- scoreStatus：FINAL / PENDING / NOT_APPLICABLE；只有 FINAL 的分数用于正式排行。
- reviewState：自动结果与最新有效复核结果的引用，不覆盖机器原始结果。

业务结论允许“不合格且覆盖未完成”：例如已确认否决但另一个计分项异常。执行成功、业务合格、评分最终状态不能共用一个 status。

### 4.4 执行顺序

解析方案与权限 → 固定数据/配置 → 适用性判断 → 逐项目/标签依赖执行 → 标准化事实 → 业务结论与标签投影 → 独立评分 → 保存分层结果 → 更新统计。

适用性判断本身需要模型时也计入执行与错误处理。资源消耗按实际调用记录，不因两个业务输出复用事实而重复计费记录。

## 5. 迁移与兼容策略

### 5.1 版本化兼容，不覆盖历史

1. 引入明确的 executionSchemaVersion 与 scoringPolicyVersion。
2. v1 任务使用原快照和旧评分语义展示；不补推未知标签，不重算历史分数。
3. v2 任务仅以方案/任务执行快照为策略权威来源；Agent.mode 不再参与新任务调度。
4. 旧 Agent 配置保留可读与审计。迁移工具提取其中的规则集和模式到候选方案策略，LLM 能力另存新版配置；不就地改历史快照。
5. 旧 RULE_ONLY Agent 可作为历史资产保留；新纯规则方案不要求构造空 Agent。
6. 旧规则 deduction/veto 作为迁移建议值和 v1 读取来源；v2 评分表成为唯一计分来源。不能两个来源相加。
7. 旧 ALL/ANY 聚合的模板需生成差异报告：保留 legacy 政策或专家确认新逐项政策；对比样本后发布，不自动转换为“等价”。
8. 旧标签结果按“历史命中投影”展示；不将缺行批量回填为明确否认或 UNKNOWN，除非有可核验的新运行依据。

### 5.2 迁移执行次序

- 只读盘点：任务/Agent/规则类型和模式分布、缺失版本、孤立引用、既有标签与复核记录。
- 生成候选方案与差异报告，不直接发布；按组织范围验证访问权限。
- 选择代表模板做同数据回放，区分预期语义变化与回归缺陷。
- 双读兼容、新建任务灰度切 v2；任务一旦创建即按自身版本执行，不中途切引擎语义。
- 回滚只切新任务入口到旧路径，保留新增数据与正在执行的版本化处理；不得删除新数据或用旧代码错误解释 v2 快照。
- 稳定后再决定旧入口的隐藏与退役，不在首期删除字段、表或历史 API。

数据库变更使用拥有方的增量迁移，不能改写冻结基线；菜单与权限变更归组织中心迁移。迁移前有备份、dry-run、数量核对与失败恢复方案。

## 6. 分期与研发工作包

以下为依赖顺序，不是工期承诺。开始开发前由团队依据代码和数据盘点估算。

### R0：契约与迁移验证

产物：领域/API 状态契约、评分公式测试样本、旧模式/ALL/ANY 对照样本、首批业务模板标准、数据迁移盘点。

退出条件：业务确认模板责任人、评分政策、允许调整范围；研发与测试能用固定样本算出唯一预期结果。

### R1：可上线的完整业务闭环

| 工作包 | 主要职责 | 前置关系 |
| --- | --- | --- |
| A 方案与版本 | 聚合、发布指针、依赖锁定、覆盖参数校验、版本差异 | R0 |
| B Agent 解耦 | 新旧配置适配、能力校验、工具/skills 模式限制解除与授权 | R0；与 A 对齐引用契约 |
| C 执行与评分 | v1/v2 分路、逐项路线、检测去重、状态映射、独立计分、幂等 | A/B 契约稳定 |
| D 基础标签融合 | 标签与检查依赖统一、明确否认/未知/冲突/错误、基础画像输出 | A/C；复用现有标签体系 |
| E 试跑与发布校验 | 草稿同引擎验证、修订绑定、正式统计隔离、发布验证 | A/C/D |
| F 使用与专家界面 | 模板列表/详情、三步任务、专家编辑、Agent 新向导 | A/B/C API 可联调 |
| G 结果与质量改进 | 项目结果、评分表、画像、证据、现有复核适配、版本化统计 | C/D；不能另造结果中心 |
| H 权限与灰度迁移 | 组织菜单/API 资源、使用/编辑分权、迁移对比与回滚演练 | A–G 集成 |

R1 不能把所有标签能力推迟：现有客户画像需求至少要支持确定值、未知和冲突的基本语义。高级派生与丰富图表可以后置。

### R2：模板复用与运营增强

离散评分档位、受控派生标签、常用设置管理增强、模板版本批量对比/升级、更多样本评测、成本与覆盖策略优化。若 R1 得分制延期，需先确认范围，并将该模板类型明确禁用而非做半实现。

### R3：规模化质量运营

跨团队模板治理、长期质量趋势、经过标注样本验证的效果评测、策略实验与运营闭环。实时语音/流式质检与独立申诉门户需另立方案。

版本治理本地实现补充（B151–B153，2026-10-04）：派生来源在既有 `POST /api/iqc/schemes` 创建契约中输入，复用 `iqc:scheme:create`、同一审计事件和不可变发布历史，不新建版本库。服务端校验来源方案范围、启用状态、精确版本及快照摘要，从已发布快照复制业务定义；来源配置由服务端读取，拒绝请求体携带可变业务定义。新草稿记录直接来源方案 ID/名称/编码、版本与摘要，后续修订不改变来源。普通模板用户可通过既有 `iqc:scheme:view` 查看启用模板的分页历史并按确切版本建任务；归档历史版从普通列表隐藏，新任务与派生草稿拒绝使用归档版。专家复用既有 `iqc:scheme:publish` 和发布端点归档/恢复已被取代的版本；当前版本不能归档，快照与既有任务保持，发布指针不变。新增迁移 `V1.1.31`、`V1.1.32`，新版服务使用这些列前必须先完成迁移。该本地功能记录不替代审批策略、正式发布门禁或 MySQL/网关/浏览器环境验收。

## 8. 风险与交付纪律

| 风险 | 控制措施 |
| --- | --- |
| “方案”只换名称，后台仍要求 Agent | U01/U02 作为上线阻断项，前后端同时验证 |

| 复核直接改总分破坏解释 | 项目级修正后按冻结政策重算；保留旧复核兼容 |
