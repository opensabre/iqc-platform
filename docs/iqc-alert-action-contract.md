# SEND_ALERT owning-service contract

Status: contract, evidence validation, preparation service and action adapter implemented. Seventeen focused tests pass, including real Feign child-context override and signed loopback POST/GET with caller-context preservation. Production deployment and actual cross-service acceptance remain outstanding.

Reuse `base-sysadmin` notification scenes, templates, channels and `NotificationRecord`. IQC owns no notification table or delivery provider. The internal client sends with POST and reconciles using GET at `/internal/iqc/notifications/{requestId}`. The request identity is the existing action's 64-character lowercase SHA-256 idempotency key.

Configuration freezes `sceneCode`, explicit `SMS` or `EMAIL`, `target` and bounded textual `args`. It rejects automatic channel selection, arbitrary callbacks, additional fields and non-text parameters. Actual rendered template content is frozen by the notification service at its first durable reservation; IQC task publication does not freeze that content.

`notification-declared-request-v1` independently binds the original declaration. Encode schema, scene, channel and target as UTF-8, each preceded by a signed big-endian int32 byte length. Then encode the int32 argument count and keys/values in Java natural string order, using the same length framing. SHA-256 yields lowercase hexadecimal. IQC configuration rejects null argument values; the owning protocol additionally supports null framing with length -1 for legacy records.

Accept success only when status schema is `iqc-notification-status-v1`, request identity and independently calculated declared hash match, record ID is 32 lowercase hexadecimal characters, final rendered-content request hash is 64 lowercase hexadecimal characters, status is `SUCCESS`, and a bounded nonblank channel receipt is present. Retain the owning record ID as action evidence/result reference. The final hash is an owning-service assertion; IQC cannot recompute it without template content. Missing or contradictory evidence returns `UNKNOWN`, never a confirmed failure or permission to resend.

`SendAlertPreparationService` performs source and claimed-attempt checks in a short local transaction. Send preparation requires current background grants, frozen owner bounds, original policy/condition/input and a matching RUNNING attempt. Historical lookup instead uses the original historical source with read-only isolation; it performs no claim or send authorization refresh. There is no notification client dependency inside this service.

`SendAlertActionAdapter` rejects execution inside a transaction, invokes preparation through its service dependency and then sends with the original key. Reconciliation similarly invokes historical preparation and GET only. Timeout, invalid proof and failed result envelopes remain UNKNOWN with no automatic resend. The action registry discovers the component by exact type/version. Local tests must establish these behaviors before treating the adapter as validated.

`IqcNotificationFeignConfiguration` is attached only to the notification client's child context. Its same-name interceptor replaces the inherited default while reusing framework credential stripping/signing; the request factory issues only `iqc-platform` to `base-sysadmin`, first-hop `service:iqc-platform` with empty roles/scopes/authorities/parent/extensions. Disabled signing fails closed. Caller claims and user context are untouched. The application explicitly registers the notification Feign interface.

Remaining integration gates: send resource/grants migration and validation; actual preparation proxy/SQL verification; actual MySQL notification migration validation; signed cross-service integration and action execution tests. The notification endpoint accepts only a first-hop service principal with empty role/scope/authority lists, so default inherited user-hop signing is insufficient. Existing action claim/settlement and historical-source validators are reused. No remote call may run inside the preparation or analysis transaction.

Validation: `SendAlertConfigurationTest` 2, `SendAlertReceiptVerifierTest` 3, `SendAlertPreparationServiceTest` 5, `SendAlertActionAdapterTest` 6 and `SendAlertFeignIdentityTest` 1 pass with no failures/errors/skips. Preparation/adapter tests use source/mapper/client substitutes; they do not establish actual database proxy commit or the real notification HTTP/filter/persistence chain.
